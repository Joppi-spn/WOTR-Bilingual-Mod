# WOTR 双语 Mod — MVP 产品设计方案

## 1. 项目背景

本项目旨在为《Pathfinder: Wrath of the Righteous（正义之怒）》开发双语文本 Mod。

目标是在游戏原有中文文本的基础上，同时显示对应的英文文本，例如：

```
坚韧豁免
Fortitude Save
```

项目主要用于：
- 游戏过程中进行中英文对照
- 辅助理解游戏文本
- 辅助英文学习

当前优先验证技术可行性，不追求一次完成完整功能。

## 2. MVP 目标

MVP 的核心目标：

> **让游戏中的中文文本能够通过对应的英文文本进行补充显示。**

需要完成：

1. 读取中文和英文语言数据
2. 根据 Localization Key 匹配中英文文本
3. 生成双语文本
4. 尽可能保持游戏原有格式
5. 正确处理缺失的语言文本
6. 在游戏中实际加载并显示

## 3. MVP 范围

| 功能 | MVP |
|---|---|
| 中文 + 英文同时显示 | 是 |
| 中英文自动匹配 | 是 |
| 读取游戏语言文件 | 是 |
| 保留 Localization Key | 是 |
| 保留占位符 | 是 |
| 保留换行/标签等格式 | 是 |
| 缺失翻译处理 | 是 |
| 游戏内实际显示 | 是 |
| Mod/插件加载 | 是 |
| 设置界面 | 否 |
| 多语言支持 | 否 |
| 自动翻译 | 否 |
| 自定义显示样式 | 否 |
| 完整文本编辑器 | 否 |

## 4. 核心使用流程

```
游戏原始语言数据
        ↓
读取中文文本
        ↓
读取英文文本
        ↓
通过 Key 匹配
        ↓
生成双语文本
        ↓
Mod / 插件加载
        ↓
游戏显示双语文本
```

例如：

```
Key:
Spell_FortitudeSave

中文：
坚韧豁免

英文：
Fortitude Save
```

最终：

```
坚韧豁免
Fortitude Save
```

## 5. 缺失文本处理

MVP 不要求所有文本都必须存在对应翻译。

基本规则：

```
中文存在 + 英文存在
→ 显示双语

中文存在 + 英文不存在
→ 至少保证中文正常显示

中文不存在 + 英文存在
→ 根据实际加载机制决定是否显示英文
```

无论哪种情况，都不能因为缺失翻译导致游戏文本系统崩溃。

## 6. 格式兼容

语言文本可能包含：

- 占位符
- 换行符
- 特殊字符
- XML/HTML 类标签
- 富文本标记
- 动态变量

例如：

```
获得 {0} 点伤害
```

不能因为添加英文文本而破坏占位符等原有格式。

因此文本处理程序必须尽可能保持原始格式。

## 7. 当前技术假设

以下内容目前**不能直接视为确定结论**，需要通过游戏文件和实际运行进行验证：

### 7.1 语言文件格式

需要确认：

- 中文语言文件的位置
- 英文语言文件的位置
- 文件格式
- 编码方式
- Key 的组织方式

### 7.2 中英文 Key 是否一致

需要验证中英文语言数据是否可以通过相同 Key 一一对应。

如果不能，需要进一步研究匹配规则。

### 7.3 游戏语言加载机制

需要确认：

- 游戏启动时如何加载语言文件
- Mod 是否能够覆盖原始文本
- 是否能够在不修改游戏原文件的情况下实现
- 是否存在可用的 Mod API

### 7.4 文本显示限制

需要确认游戏 UI 是否允许在原文本后追加第二行英文，以及：

- 长文本是否会溢出
- UI 是否自动换行
- 富文本标签是否会影响显示

## 8. 简易前置 Demo

在正式开发之前，先完成一个最小 Demo。

Demo 不要求进入游戏。

第一阶段只验证：

```
读取两个语言文件
        ↓
提取 Key + 文本
        ↓
匹配相同 Key
        ↓
生成双语文本
```

例如：

```
输入：

CN:
ID_001 = 坚韧豁免

EN:
ID_001 = Fortitude Save

输出：

ID_001 = 坚韧豁免\nFortitude Save
```

如果这一阶段成功，再继续验证游戏加载机制。

## 9. MVP 验收标准

MVP 至少满足：

1. 能读取实际游戏语言数据
2. 能正确识别语言 Key
3. 能匹配中英文文本
4. 能生成正确的双语文本
5. 不破坏占位符和基本格式
6. 缺失翻译不会导致程序异常
7. 能通过 Mod/插件机制加载
8. 能在游戏中看到实际双语文本
9. 不需要修改游戏本体文件即可运行，或明确记录必要的修改方式

## 10. 风险与待验证问题

当前主要风险：

- 游戏语言文件可能不是普通文本格式
- 中英文 Key 可能存在差异
- 文本可能经过压缩、打包或特殊处理
- 游戏可能限制语言资源的外部覆盖
- UI 可能存在文本长度限制
- 动态文本可能无法简单通过 Key 匹配
- Mod 加载机制可能需要特定框架

这些问题不在设计阶段直接假设解决方案，而是通过后续 Demo 和实际测试逐项确认。

## 11. 下一阶段

产品设计完成后，进入：

**简易前置 Demo**

首先确认：

1. 中文语言文件在哪里
2. 英文语言文件在哪里
3. 文件是什么格式
4. Key 是什么结构
5. 中英文 Key 能否对应

这些信息确认后，再确定具体的文本处理方案和 Mod 加载方案。
